知卷｜长期开发、跨会话接手与回归控制手册

交接包 v1.4 · 2026-09-16。产品与 32 项实施基线仍为 v1.3。本文是新增开发机制的操作手册；不是产品已经上线的声明。

01 这次真正补上了什么

项目增长后需要分别解决三件事：知道当前事实、快速找到本轮工作入口、验证旧行为没有被改坏。这次不依赖聊天历史或另一个“记忆 Agent”，而是在仓库中建立可版本化记录，并提供可以本地运行的脚本。

能力 本次状态 不能误解为
功能账本与实际任务覆盖层 已提供并有一致性校验 产品功能已经实现
任务上下文整理与 Git 路径变化查询 已实现并做本地临时 Git 仓库测试 完整代码语义分析、自动找到所有依赖
按任务/会话交接 已实现创建、现场快照、差异提示；默认不覆盖 自动总结未说出的事实或保存模型私有推理
证据范围指纹与过期识别 已实现代码/登记范围/依赖的字节比较 可信签名、绝对防造假、跨环境自动保证
离线检查 runner 与 CI 文件 本地已运行；远程 CI 未执行/未启用 已启用 GitHub 保护规则或应用回归
10 项关键产品回归行为 已映射到功能和验收，应用测试待实现 已有可运行网页/数据库/导出 E2E

当前 15 项功能记录中，14 项为未来产品功能、均 NOT_STARTED；1 项为本次真实开发工具。原 32 项实施任务、47 类运行验收仍是未执行模板，不因为新增工具而变成已验收。

02 事实放哪里：一个事实只维护一处

AGENTS.md 只保存稳定约束、命令与入口。docs/project-map.md 说明模块分工；progress/features.yaml 是实际功能、依赖及验证索引；progress/work.yaml 是实际任务状态；acceptance-runs/ 保存运行事实；progress/handoffs/ 保存会话接手信息；docs/decisions/ 解释经批准的取舍。

progress/current.md 是派生摘要，修改账本后运行 status --write 生成，不另外手填一份状态。报告记录一次测试；功能的 last_evidence 只引用它，不在多个文档重复抄写“已通过”。同一源码版本在不同环境测试的结果可以不同，应分别记录。

原 execution/task-index.yaml 是 32 项实施基线；原 acceptance/ 是运行用例定义。不要用修改模板状态来冒充运行。实际进度可持续在 progress/work.yaml 更新。通过原有基线检查，不代表实际进度永远不能前进。

后续有批准的新需求/缺陷任务时，将完整任务定义追加到 progress/extra-tasks.yaml 的 tasks 列表。其字段与原任务卡一致：id、phase、title、depends_on、source_files、target_files、implementation_steps、failure_action、acceptance_refs 等。新编号不得与原任务冲突；依赖图不得循环；任务存在不等于已开始。工具将两份计划合并读取，但不重写原始 32 项基线。

变更的“期望行为”由批准需求/决定说明；代码/测试展示“实际行为”。两者冲突要登记差异，而不是自动认定代码或旧文档永远正确。

03 首次接入现有项目：先盘点，不能一键覆盖

新知卷工程：当前包没有应用源码，按 M0 任务授权建立真正的工程，保留本工具作为开发支持。不要执行尚不存在的应用启动命令。

已有项目：先检查工作目录、分支、未提交修改，制作可恢复检查点；在独立工作分支合并新文件。保留原源码、测试、CI、AGENTS 与负责人设置。尤其不能用本包的离线工作流替换原有应用回归流水线。

逐模块盘点现有功能：找到前端入口/接口/实现/测试，写出用户可见行为和限制。没有证据的旧功能可以标 IMPLEMENTED + 验证 NOT_RUN，而不是凭聊天概括标“已验收”。实现路径只说明文件存在，真正行为需要测试和审查。不要批量从函数名称推断全部功能。

记录根应是实际 Git 根。若把整个材料放到 baseline/ 而根在其他位置，需要迁移相关路径并调整脚本的数据读取；当前工具遇到父目录 Git 仓库会拒绝自动借用，防止误分析别的项目。

首次安装测试依赖需在允许联网的环境中执行。requirements-ci.lock 是本次离线依赖实测精确版本，不是生产 Python/Node/Hermes 依赖锁。依赖安装和 Actions 获取需要网络，本次未替用户部署任何远程服务。

04 每轮开发怎样执行

开始：先读根 AGENTS 和 current 摘要，明确任务 ID。生成本任务上下文，核对现场，再补读必要源码、契约、测试和更具体的目录规则。AGENTS 是常规 Markdown 入口，工具的实际读取行为要核对，不能假定所有编程工具都会自动完整加载。[L1]

python tools/project_memory.py context --task M2-05
# 已有本地 main 时包含从共同祖先到 HEAD 的分支变化：
python tools/project_memory.py context --task M2-05 --base main

未指定 --base 时，仅汇总当前暂存、未暂存及未跟踪路径；不能说已经查过全部已提交变化。git diff 不同形式分别比较工作区、暂存区和提交；本工具显式组合它们，并用不做重命名折叠的路径列表保留旧/新文件名。[L2]

改之前：填写 progress/templates/change-impact.md。指出行为、受影响模块、调用方、共享 schema、旧行为不变量、迁移和失败恢复。路径数量不能替代业务影响范围。脚本会辅助定位，但不能代替阅读。

python tools/project_memory.py impact --task M2-05 --base main
# 非 Git 目录也可以显式输入待改路径做规划提示：
python tools/project_memory.py impact --task M2-05 --path services/api/domain/revisions.py

实现：围绕一个可验证行为小步修改。补测试、检查调用方、保持类型/协议一致。修缺陷尽量先加一条能复现失败的测试，再修代码，避免同时改实现和预期掩盖问题。不要无关重排整个仓库，也不要为“目录齐全”创建大量空壳。

验证：先局部后关联回归，必要时扩大到契约、队列、权限、导出和真实模型。开发助手必须报告实际命令、退出码、测试范围、环境、失败/跳过/未执行。出题质量验证与软件单元测试分开。

检查点：完成一个可验证步骤就更新记录，不能等用户说“结束会话”才做。是否提交 Git 服从用户授权；不自动推送或修改分支保护。来不及完成就写清未提交改动和下一动作，不能假装 DONE。

05 功能账本怎样更新

每个功能使用稳定 ID。任务 ID 追踪一次工作，功能 ID 追踪长期行为；多个任务可共同实现一个功能，一次公共模块改动也可影响多个功能。文件重命名时更新实现与 watch_paths，功能 ID 不跟着随便变。

现有 FEAT-REGEN 的关键行为是只替换选定槽位、不修改其他题，且使相关旧检查失效。implementation_paths 在真实代码存在前保持空；target_files 的未来路径不能直接填成完成证据。

字段 谁维护/什么时候更新
implementation 开发者据实写 NOT_STARTED/IN_PROGRESS/IMPLEMENTED/DEPRECATED
task_ids 关联已定义任务，不编造编号
requires 依赖的功能；修改后重做影响映射与证据范围检查
watch_paths 需要与证据绑定的实现、测试、配置路径；使用本工具 glob 语义，不是 gitignore
implementation_paths 真实存在的实现入口；模板/Protocol 不当成运行实现
invariants 以后任何修改都应保留的业务行为；变更需决策与新测试
required_suites 本功能所要求的测试组，不为放行而删除
last_evidence 指向最近实际报告；没跑就保持 null
limitations 未覆盖能力/环境/人工复核要求

实现状态和验证状态分开。OFFLINE_PASS 是脚本根据登记报告和当前范围派生，不能直接在 YAML 填一个 verified=true。报告无法读取、测试缺失、检查失败、源码或范围变化均有不同结论。

tasks 实际覆盖层的 DONE 至少需要 completed_by、completed_at、evidence_refs。脚本只检查这些字段和路径，不可能验证现实世界中的人已经签字；阶段签收仍使用现有验收与批准流程。不能把编程助手写入一个名字当成真人批准。

修改后刷新摘要：

python tools/project_memory.py check
python tools/project_memory.py status --write
python tools/project_memory.py status --check-current

默认 check 校验记录结构并报告缺失/过期证据；它不把“已实现但还没测”误当不存在，也不自动签收。需要对已实现功能严格要求离线证据时加 check --strict-evidence；产品真实验收不由这个离线格式承接。

06 新会话如何快速接手

context 输出任务目标、前置任务实际状态、步骤、直接和受影响功能、旧验证状态、最近三条会话交接、源码/契约入口、当前 Git 路径变化及建议测试。默认最大 12000 个字符，不是精确 token 预算；达到上限会标 CONTEXT_TRUNCATED，必须按提示补读，不允许把截断当完整上下文。

python tools/project_memory.py context --task M2-05 --max-chars 12000 --out progress/generated/M2-05-session-b.md

输出只能写进 progress/generated/ 的新文件，不覆盖已有文件；这些可重建材料不需要全部提交 Git。工具不读环境变量内容、raw diff、完整源码或模型日志，不对整仓库做向量索引。Git 查询只用于当前现场与选定基准；没有 Git 就显示 NO_GIT，不自动 init、fetch 或制造提交。

接手时先回答四个问题：已有何实现和证据，哪些证据需要重测，当前改动影响什么，下一步具体做什么。然后再实施。只读取入口不代表不理解代码；需要精读本轮待修改及受影响部分，避免无差别重读完整方案。

相关代码修改、功能范围缩小、新增匹配文件或依赖修改都会让登记证据失去当前范围适用性。即便当前字节一致，也只说明登记范围一致；环境、服务端模型变化或未登记动态依赖仍需额外检查。

07 交接不能只写一句“下次继续”

每次交接使用 <task>--<session>.yaml，不是全局唯一 HANDOFF。唯一会话名可使用开发者别名和顺序号，不填学生或敏感个人信息。

python tools/project_memory.py handoff --task M2-05 --session dev-a-checkpoint-001 --summary "据实写当前完成与阻塞" --next "据实写下一个具体动作"

命令创建版本/文件指纹快照，但不替你断言 completed。执行者补充：已完成行为与入口、仍失败的测试、已批准决定、尝试但失败的方案及原因、尚待审核、实际证据、下一步应先读的内容。只记录简洁工作事实，不保存模型私有推理或整段聊天。

下一检查点用新的 session 名，不覆盖上一份。并行会话分别写交接，features/work 是共享事实层，合并时仍要检查冲突。Git worktree 支持多个工作树，但它不隔离共享数据库、端口、账户或生产文件权限。[L3]

工具显示交接 HEAD/分支和登记文件是否变化；最新时间戳不等于最可靠。多条不同分支的交接需人工选择当前分支适用的记录；更早文件按需读。历史交接归档而不默认注入全部上下文。

突然中断时，从最近检查点 + Git 未提交修改 + 实际报告恢复。若文件发生修改而交接未更新，不先清理现场；先核对是哪次授权工作留下的变化。

08 怎样选择回归，而不只看改了几个文件

本工具将 watch_paths 命中作为直接影响，再沿 requires 的反向关系找到依赖者。全局 schema、配置、重要锁文件或 CI 的变化扩大范围；未映射路径列出来，建议全套离线基线并要求人工补充。

这不是抽象语法树、类型调用图或完整动态依赖分析。新增文件、跨服务协议、运行时反射、浏览器资源和模型行为都可能超出映射。不能把“没有命中”当作“不会影响旧功能”。只读几个文件之后，也不能武断宣称不存在回归。

quality/regression-map.yaml 把关键行为映射到稳定编号、功能、原验收和应用测试组。比如：REG-001 单题重生成不改别题，REG-002 改题使旧证据失效，REG-003 学生数据不含私有答案，REG-004 取消后的迟到结果不回写，REG-006 检查超时不返回 PASS，REG-008 最终文件变更后重新审批。

当前这些应用测试路径为空且标 NOT_IMPLEMENTED，因为真实应用尚未写出来。现有 publish_gate 参考规则测试只能提供局部逻辑保护，不能冒充网页点击、真实数据库事务或文件生成回归。开发到相应功能时，先落实真实测试，再填写 actual_test_paths，修改测试组目录及独立应用 CI。

改动 建议验证
普通局部代码 类型/格式/局部单元和直接调用方
API/schema/分值/版本 契约、调用方、兼容、数据库与旧行为回归
Worker/取消/恢复 重投、租约、迟到、外部未知状态、实际用量
权限/公开投影 两个测试身份/组织的拒绝访问、答案不泄露
排版/资产 实际公式/图形/分页、学生教师投影、审批版本
Hermes/模型/Skills/检查规则 离线边界测试 + 授权的真实工具调用/隔离/分学段内容回归
正式发布 已承诺范围的完整验收、教研、恢复和签收

09 测试报告怎样成为可核对证据

可运行的 runner 只执行 quality/suites.yaml 中 IMPLEMENTED 且 OFFLINE 的命令。它不安装依赖、不启动模型或数据库，不自动运行上下文里推荐的任意 shell。执行仓库 Python 仍然执行代码，shell=False 不是安全沙箱；应先审查仓库来源和命令。

python tools/run_quality_checks.py --suite all-offline --feature FEAT-DEV-MEMORY --out acceptance-runs/devtools/local-run-001

6 个已有离线组分别是全量单元、Schema/API 基线、验收材料、阶段实施映射、开发工具专项和记录一致性。全量单元已含专项，不相加宣传测试数量。单元 runner 对零测试、skip、expected failure、执行错误均不会给整轮 PASS。

报告记录开始与结束时间、代码范围快照、功能声明指纹、Git HEAD/变化路径、Python/包版本、每组命令、退出码、用时、脱敏日志与日志指纹。范围在执行中变化，则结果无效，需要在稳定工作区重跑。报告生成后不自动修改功能状态；据实引用 last_evidence 再刷新摘要。

scope 指纹包含本功能和依赖的登记路径及全局路径，不包含报告自身或 last_evidence 指针，避免“报告引用自身”循环。遗漏 watch_paths、隐式环境依赖或远端模型更新不会神奇地被字节哈希发现；人工必须确认范围和环境。OFFLINE_PASS 表示报告所记环境的离线通过，不表示新机器已实测同样结果。

脚本核对日志字节指纹，但这不是签名；有写权限的人仍可能一起修改报告、代码与规则。不能把 SHA256 当身份认证或完整安全审计。可信度由代码审查、受保护 CI 和真实执行证据共同支撑。

10 CI 怎样启用，以及现在保护不到什么

工作流位于真实仓库根 .github/workflows/ci.yml。当前只是已生成配置，本次没有创建远程仓库、推送文件或执行 GitHub Actions，也没有开启仓库分支保护。

先在独立 PR 验证流程安装依赖、执行 6 个组、保存报告。Actions 使用核查过源码的固定提交；依赖版本使用本次离线清单。CI 选 Python 3.12，而本地实际版本以报告为准；尚未在远程 runner 完成兼容验证。不要把文件存在当执行成功。[L4]

管理员在实际仓库设置必要检查和审查规则，并确定谁能够改测试、workflow、契约和权限代码。GitHub 提供保护分支和必需检查设置，但是否可用及如何配置要以实际账户/仓库为准；不能由 ZIP 自动代办。[L5]

本工作流不用 paths 过滤、不触发 pull_request_target、不接模型密钥、不部署。最后的 required-checks 使用 always() 并断言 offline job 真正 success。GitHub 文档说明 skipped job 可显示成功，因此不能只看一个绿色图标；汇总检查需要明确验证必需结果。[L6]

当前 CI 仅保护这些离线材料、参考规则和开发工具。它不会编译尚不存在的 React/FastAPI，不运行数据库/权限/渲染/真实模型测试；离线绿灯不能批准应用合并和上线。随着产品实现，应保留这套检查并新增应用流水线，把本阶段实际要求的测试作为必需检查；不能把所有未来测试长期列为 PLANNED 却宣称回归已完整。

可用 .github/CODEOWNERS.example 作为设置说明，填真实账号/团队后才可能生效。未知 fork 的代码不可用带生产秘密的高权限工作流执行。CI 证据默认只保留一段时间，需要长期存档的脱敏记录按数据保留规则移入受控存储，不永久提交所有日志。

11 实际操作演练与失败分支

记录过期演练：对一个已登记离线报告的开发工具文件做授权修改，运行 status 应出现 STALE；重新执行相关测试、更新 last_evidence 再刷新摘要。演练不能破坏用户未提交工作；最好用独立副本或工作分支。

交接冲突演练：同任务用不同 session 创建两份交接，检查都保留；重复同名创建必须失败，不覆盖旧记录。并行分支核对摘要显示的 HEAD/分支差异。

未知路径演练：impact 显式传一个尚未登记的新模块路径，输出 unmapped_paths，并提示人工补充；不能返回“没有影响”。只有注册映射不等于测试完成。

跳过演练：测试框架返回 skipped 或零测试时，runner 非零退出，不将它作为质量通过。本包已在临时测试夹具验证此行为；未把夹具结果当真实应用回归。

故障 正确动作
没有 Git 显示 NO_GIT，核对文件事实；不制造 HEAD
--base 不存在 命令失败；确认正确本地基准或经授权获取，不假设无变化
账本路径不存在 报错/修正引用；不能靠猜测补实现
旧报告日志变了 标 INVALID，查明原因后重跑，不能只改哈希掩盖改动
测试超时 TIMED_OUT、非零；保留失败证据，不直接加时至无限
真实服务不可用 产品验收 NOT_RUN/BLOCKED；可以继续无依赖的离线工作
源码和方案冲突 登记差异、影响和批准变更，不静默选有利版本
模型上下文不足 写检查点和必要索引，新会话按任务续接，不灌入全部旧聊天

12 开发记录的维护节奏

每个可验证改动：更新功能/任务与测试证据。每个会话检查点：记录现场、已做/未做、失败方案和下一动作。每次 PR：检查相关旧行为、记录变更决定、确认测试不是被放宽。阶段评审/发布：再同步正式 Word/HTML/ZIP，保存版本与范围。

日常不需要每改一个函数就重写 70 页方案；也不需要不断向根 AGENTS 加入项目历史。根入口保持短，模块指导就近放，完整规范按链接读取。项目变大后可把功能账本按模块拆分，但要同时调整工具加载和验证，不能用多个冲突账本维护同一事实。

不承诺“永不回归”或“新会话完全不用理解项目”。可交付效果是减少反复找入口、让已实现功能有验证依据、让旧结论失效可见，并让关键旧行为随修改重测。最终仍依赖测试覆盖、教研判断、代码审查、权限和真实运行。
